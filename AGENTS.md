# Инструкции для работы над «Кэшбэк рядом»

Перед изменениями прочитай `PROJECT_CONTEXT.md` и актуальный `README.md`. Документ контекста хранит продуктовые решения, план, промпты и статус; README — команды запуска. Сверяй исторические результаты с текущими файлами и состоянием среды.

## Инструкция пользователя о субагентах

Не используй субагентов для простых задач с низким уровнем риска или ограниченной областью, если один агент может надёжно выполнить работу самостоятельно. Используй субагентов, только если ожидаемая польза оправдывает дополнительные затраты токенов и сложность.

Если используешь субагентов, ставь каждому чёткую и узкую задачу. Объединяй их результаты, разрешай противоречия и принимай окончательное решение самостоятельно. Следуй также действующим ограничениям среды на делегирование.

## Правила проекта

- Общий Flutter-проект Android/iOS. На Windows проверяем Android; iOS не считать проверенным без сборки на macOS.
- Пользовательский интерфейс и документация — на русском, простым языком.
- Разделять интерфейс, логику, модели и доступ к данным.
- Не выдавать демонстрационные категории за пользовательские данные.
- Сохранять месяц И год и точное название категории банка.
- Не приравнивать бонусы Спасибо к рублям. Не объединять банковские категории по одному лишь сходству названий.
- Перед постоянным хранением учесть стабильные ID и миграции. Сохранить исходное название при будущем сопоставлении категорий.
- OCR подключать через заменяемый адаптер после проверки кириллицы и выбранных строк; не привязывать пользовательские данные к формату движка.
- До первого магазинного билда определить окончательные applicationId/bundle ID и релизную подпись. Текущие идентификаторы предварительные; реестр важных решений — раздел 14 PROJECT_CONTEXT.md.
- Черновик импорта и подтверждённые категории — разные сущности. Не перезаписывать данные до подтверждения пользователем.
- Не логировать скриншоты, банковские реквизиты и распознанные персональные данные. Исследовать локальный OCR; внешний сервис требует отдельного решения пользователя.
- Не добавлять сервер, регистрацию, аналитику, монетизацию или виджеты вне текущего согласованного этапа.
- Инструменты, SDK и крупные кэши по возможности держать на D:. Не переносить их в Git.
- Проверять Git status перед работой; сохранять чужие незакоммиченные изменения. Не применять разрушительный откат и force push без явного запроса.
- Репозиторий GitHub должен оставаться Private. Не менять видимость и не приглашать участников без запроса пользователя.
- После завершения этапа обновлять разделы статуса и проверок в PROJECT_CONTEXT.md; README — при изменении запуска. Не отмечать запланированное как реализованное.
- Тесты выбирать по риску и поведению, а не писать проверки, просто повторяющие код.
